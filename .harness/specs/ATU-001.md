## 1. Contexto y Problema

Hoy la app solo permite localizar y marcar los 58 pozos de Tears of the Kingdom. El objetivo del proyecto es ser una guía de coleccionables, y la siguiente categoría son los **atuendos** (piezas de armadura y ropa). El usuario debe poder ver en el mapa dónde se obtiene cada pieza, marcarla como conseguida y llevar su progreso por separado del de los pozos, todo guardado en `localStorage` como hoy.

Según `.harness/context/system-overview.md` (sección 0), la app está acoplada a "pozos" en `window.TOTK_WELLS`, la constante `WELLS`, la clave `totk.wells.found.v1`, el total `58` escrito en `index.html`, los textos de UI y los íconos de gota. Esta spec introduce una segunda categoría sin romper la de pozos.

2. **Fuente de datos:** el desarrollador entrega el export de atuendos con nombre y coordenadas (por ejemplo, desde ZeldaMods / TotK Object Map, la misma fuente de los pozos) y lo enlaza aquí: `[RUTA O URL DEL EXPORT]`. **El agente no inventa ni completa registros ni coordenadas de memoria.**
3. **Quality gates:** definir los comandos de linter, tipado y tests en la sección 4 de `AGENTS.md` (hoy están en `[DEFINIR]`). Sin ellos el agente se detiene al verificar.
4. **Contrato:** copiar el modelo de la sección 3.1 de esta spec a `.harness/context/data-contracts.md` como "Modelo de Atuendo".

### Fuera de alcance

- Atuendos que solo se obtienen en las **islas del cielo** o en el **subsuelo**: la app solo tiene el mapa de superficie. Se registran en el dataset con `layer` distinto de `surface` y no se pintan; un spec posterior añadirá esas capas.
- Atuendos que se obtienen por tienda, misión o amiibo sin un punto fijo en el mapa.
- Mejoras de armadura con las Grandes Hadas, efectos de set y bonificaciones.
- Persistir la categoría activa entre sesiones.
- Cambios en el comportamiento o los datos de los pozos.

## 3. Contratos de Datos

### 3.1 Modelo de Atuendo (`data/outfits.json` y `window.TOTK_OUTFITS`)

```json
{
  "id": "0001",
  "name": "Nombre de la pieza",
  "set": "Nombre del conjunto",
  "slot": "head",
  "layer": "surface",
  "x": 0.0,
  "y": 0.0,
  "z": 0.0
}
```

| Campo | Tipo | Regla |
| :--- | :--- | :--- |
| `id` | string | 4 dígitos con ceros a la izquierda, único dentro de atuendos. |
| `name` | string | Nombre de la pieza, tal como viene en la fuente. |
| `set` | string | Conjunto al que pertenece; `""` si es una pieza suelta. |
| `slot` | string | `head`, `body` o `legs`. |
| `layer` | string | `surface`, `sky` o `depths`. Solo `surface` se pinta en esta spec. |
| `x`, `y`, `z` | number | Mismo sistema que los pozos: `x` es lat y `y` es lng en Leaflet, dentro de `MAP_BOUNDS`. |

### 3.2 Persistencia

| Clave | Contenido | Regla |
| :--- | :--- | :--- |
| `totk.outfits.found.v1` | Arreglo JSON de `id` de atuendos conseguidos | Nueva. Se descartan ids inexistentes al leer, igual que en pozos. |
| `totk.wells.found.v1` | Sin cambios | No se renombra ni se migra. |
| `totk.wells.view.v1` | Sin cambios | La vista del mapa es compartida entre categorías. |

## 4. Criterios de Aceptación Funcionales (Gherkin / Binarios)

- [ ] **Escenario 1: Selector de categoría**
  - *Dado que* abro `index.html` por primera vez.
  - *Cuando* carga la app.
  - *Entonces* veo un selector con "Pozos" y "Atuendos", con "Pozos" activo y el mismo comportamiento que antes de esta spec.

- [ ] **Escenario 2: Atuendos en el mapa**
  - *Dado que* el dataset tiene N atuendos con `layer = "surface"`.
  - *Cuando* activo "Atuendos".
  - *Entonces* el mapa muestra exactamente N marcadores de atuendo (agrupados con MarkerCluster), oculta los de pozos y la lista muestra los N atuendos ordenados por `id`, con nombre, conjunto y pieza (`slot`).

- [ ] **Escenario 3: Marcar un atuendo**
  - *Dado que* "Atuendos" está activo.
  - *Cuando* marco una pieza como conseguida desde el popup.
  - *Entonces* cambian su marcador y su fila, el progreso muestra `1 / N`, aparece el toast y `totk.outfits.found.v1` contiene ese `id`. `totk.wells.found.v1` no cambia.

- [ ] **Escenario 4: Progreso independiente y persistente**
  - *Dado que* marqué 2 pozos y 3 atuendos.
  - *Cuando* recargo la página y cambio de categoría.
  - *Entonces* "Pozos" muestra `2 / 58` y "Atuendos" muestra `3 / N`.

- [ ] **Escenario 5: Reinicio por categoría**
  - *Dado que* "Atuendos" está activo y tengo pozos y atuendos marcados.
  - *Cuando* confirmo "Reiniciar progreso".
  - *Entonces* solo se vacía `totk.outfits.found.v1`; los pozos conservan su progreso. El texto del modal nombra la categoría activa.

- [ ] **Escenario 6: Búsqueda y filtros**
  - *Dado que* "Atuendos" está activo.
  - *Cuando* busco por nombre o conjunto, o uso los filtros Todos / Pendientes / Encontrados.
  - *Entonces* la lista se filtra igual que en pozos, sin distinguir acentos ni mayúsculas.

- [ ] **Escenario 7: Datos corruptos o ausentes**
  - *Dado que* `totk.outfits.found.v1` contiene basura o `window.TOTK_OUTFITS` no existe.
  - *Cuando* activo "Atuendos".
  - *Entonces* la app no lanza errores en consola, trata el progreso como vacío o muestra un mensaje de "sin datos", y "Pozos" sigue funcionando.

- [ ] **Escenario 8: Sin totales fijos**
  - *Dado que* cambio de categoría.
  - *Cuando* se actualizan los contadores.
  - *Entonces* ningún contador, chip, `aria-valuemax` ni texto de lista muestra `58` mientras "Atuendos" está activo.

- [ ] **Escenario 9: Paridad de datos**
  - *Dado que* existen `outfits.json` y `outfits.js`.
  - *Cuando* se comparan sus registros.
  - *Entonces* son idénticos, los `id` son únicos y todos los registros `surface` están dentro de `MAP_BOUNDS`.

- [ ] **Escenario 10: Regresión de pozos**
  - *Dado que* "Pozos" está activo.
  - *Cuando* uso búsqueda, filtros, marcar, centrar, reiniciar, atajos `/` y `Escape`, y el panel en móvil.
  - *Entonces* todo se comporta igual que en el commit base.
